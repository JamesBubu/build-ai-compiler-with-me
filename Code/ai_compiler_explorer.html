Computation Graph & Lazy Evaluation +
A Directed Acyclic Graph (DAG) is the universal IR of every AI framework. Nodes are operators; edges are tensors. The graph is constructed at definition time — no data flows until you explicitly evaluate it.
This is called Lazy Evaluation (TF 1.x, JAX). Contrast with Eager Execution (PyTorch default), where ops run immediately. Lazy graphs give the compiler room to optimize before running anything.
x = Variable("x") # just a symbol, no value z = ReLU(Add(x, y)) # build graph structure evaluate(z, {x:[1,2,3]}) # ← runtime starts here
Compile Time — the compiler reads the blueprint, runs passes, plans memory, and generates machine code.
Run Time — the hardware receives real tensor data and executes the compiled code.
Shape Inference +
Analysis Pass · Bottom-Up
Before any tensor is allocated, the compiler walks the graph bottom-up, deriving the output shape of every node from its inputs. This is essential for static memory allocation — the hardware needs to know exactly how much memory each layer needs before execution begins.
It also catches bugs early: if an Add node receives mismatched shapes, the compiler throws an error at compile time instead of crashing during a long training run.
Variable x → shape [3] Variable y → shape [3] Add(x, y) → shape [3] ← derived from inputs ReLU(add) → shape [3] ← propagated
Constant Folding +
Transformation Pass
If all inputs to an op are Constants, the compiler can pre-compute the result at compile time and replace the entire subgraph with a single new Constant node. The GPU never sees that computation — it's already been done.
Const a = [1, 2, 3] Const b = [4, 5, 6] Add(a, b) → folded to Const [5, 7, 9]
This is the exception to "compilers don't compute values." When the answer is fixed and predictable, why not compute it once and save the work?
Algebraic Simplification +
Transformation Pass
Uses basic math identities to eliminate unnecessary operations — even when variables are involved.
x + 0 → x
x × 1 → x
x × 0 → Constant(0)
"Who writes x + 0?" — other passes do. When BatchNorm is fused into Conv, its bias can become zero. Algebraic Simplification then cleans up the leftover + 0 nodes. This shows how passes chain together: each pass sets up opportunities for the next.
Common Subexpression Elimination (CSE) +
Transformation Pass
If the compiler finds two nodes performing the exact same operation on the same inputs, it merges them into one. All consumers of the duplicate node are redirected to the canonical one.
y1 = relu(x * w) # x*w computed y2 = relu(x * w) + b # x*w computed AGAIN ← wasteful # After CSE: tmp = x * w # computed once y1 = relu(tmp) y2 = relu(tmp) + b # shares tmp
In complex networks like ResNet or Inception, engineers sometimes inadvertently compute the same feature map multiple times. CSE guarantees it's computed exactly once on the GPU.
Try it: load Graph 3 (CSE demo) — it has Add(a,b) computed twice. Run CSE and watch one node disappear.
Dead Code Elimination (DCE) +
Transformation Pass · Top-Down
Unlike Shape Inference (bottom-up), DCE asks a top-down question: "Starting from the outputs, what do I actually need?"
The compiler traces backward via BFS from output nodes. Any node not reachable from an output is "dead" — it contributes nothing to the result.
Real-world impact: training graphs contain Loss and Gradient nodes. At inference time, you only need predictions — not gradients. DCE automatically removes all Loss/Backprop nodes, making the deployed model significantly smaller.
W8A16 Quantization +
Hardware Pass · Memory Bound Optimization
Modern AI hardware is fast at computation but slow at moving data. Weights in large models saturate the memory bus — this is called Memory Bound.
W8A16 quantizes weights (W) to INT8 while keeping activations (A) in FP16. The bandwidth savings are ~2×. Activations stay in FP16 because they contain unpredictable outliers that would damage accuracy if forced to INT8.
Scale = max(|W|) / 127 W_int8 = round(W / Scale) # FP32 → INT8 (stored) W_dequant = W_int8 × Scale # INT8 → FP32 (at runtime)
The compiler inserts Dequantize nodes into the graph. The hardware loads compact INT8 weights, then dequantizes just-in-time before the multiply.
Channel-wise vs Tensor-wise: a single global scale wastes precision when one channel has an outlier. Channel-wise gives each output channel its own scale.
Static Quantization (PTQ): run 100–500 representative samples through the model, record per-layer activation statistics, hardcode the scales. No dynamic overhead at runtime.
Code Generation (Backend) +
Backend Pass
All previous passes worked on Python objects in memory. But hardware cannot read Python objects. The final step is translating the optimized DAG into low-level code (C / CUDA / device-specific assembly) that a traditional compiler like GCC or NVCC can compile into machine code.
The key insight: instead of executing each node, the backend prints a string for each node in topological order.
// Unoptimized FP32: float v0 = 3.1415f; // load constant float v1 = A * v0; // FP32 multiply // After W8A16 quantization: int8_t v0 = 127; // load INT8 weight float v1 = (float)v0 * S; // dequantize float v2 = A * v1; // FP32 multiply
In production: TVM generates CUDA kernels, MLIR lowers through multiple dialect levels, PyTorch Inductor generates Triton code. The concept is identical.
Industry Frameworks +
Every pass you've used in this explorer exists in production compilers — just at industrial scale with hardware-specific backends:
TVM
Graph-level IR (Relay) → operator-level IR (TIR) → CUDA/Metal/Hexagon code. AutoTVM and AutoScheduler search for optimal loop tiling and unrolling.
MLIR
Multi-level dialects (HLO → Linalg → LLVM IR). Each dialect transformation is a pass. Used in TensorFlow, IREE, and many TPU stacks.
torch.compile
TorchDynamo captures the computation graph via Python bytecode tracing. Inductor applies fusion, quantization, and tiling, then emits Triton or C++ kernels.
XLA
Google's compiler for TPUs (and GPUs). HLO (High-Level Optimizer) IR with aggressive fusion. Used under JAX and TensorFlow.
